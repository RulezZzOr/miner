# Delivery and security audit — 2026-09-24

Scope: Studio controllers and GUI, worker boundaries, source packaging, runtime
dependencies and publication contents. This is a source review plus automated and
interactive verification, not a penetration-test certification or a claim of
complete security. No third-party or production business system was attacked.

## Functional findings and fixes

| Finding | Change and verification |
| --- | --- |
| Contradictory audit scope could reach an execution worker. | Readiness stops recognized contradictions before dispatch; complex planning requires an assessment. Revision tests prove old wording is retained and stale edits rejected. |
| Results were spread across reports; a successful command could run zero tests. | Result card binds outputs, command records and review to source state. Test commands need a recognized positive executed-test count; skipped-only results fail. |
| Restart context required re-reading loose reports. | Saved bounded handoff identifies completed/pending work and changed references. It does not override SQLite scheduling or exact task criteria. |
| Accepted changes did not reliably update reference notes. | Recoverable, conflict-checked Markdown acceptance records preserve existing text and explicit write restrictions. Notes have a separate documentation version. |
| Small changes used the same context/work budgets as larger changes. | Light/Standard/Sensitive process with smaller Light budgets, automatic risk escalation and a retained review profile. Classification remains heuristic. |
| A brief conflict still offered ineffective Yes/No approval. | A direct Revise brief action replaces those answers; the API rejects an ineffective answer as well. |
| Project selection could remain blocked after saving a form. | Selection now evaluates the current draft state instead of a stale captured flag. Browser reproduction and a regression test cover the fix. |
| Acceptance notes contained identifiers but insufficient context for the next agent. | Alpha.9 adds a bounded, attributed review summary and up to 24 relative output links with snapshot hashes. Supplied Markdown is escaped; truncation and omitted outputs are explicit. Existing notes and concurrent edits remain protected. |

## Security findings and disposition

1. **Fixed: unbounded Office archive expansion and unsafe direct chart XML parsing.**
   The reader rejects Office ZIPs above 100 MB expanded data, 10,000 members or
   25 MB per member, before Office parsing. Direct chart XML reads are capped at
   2 MB and use `defusedxml` with DTDs forbidden. Refused input exits nonzero, so
   an error cannot be recorded as a successful saved document. Tests cover entity
   declarations, oversized compressed input and normal XLSX compatibility.
   The parser choice follows [openpyxl's security guidance](https://openpyxl.readthedocs.io/en/stable/)
   and the [defusedxml project](https://github.com/tiran/defusedxml).
2. **Verified: request and file boundaries.** Existing Host/Origin/request-token
   checks, protected file paths, no-follow file access, source-version conflict
   checks, process cleanup and fixed-path mission reports remain in the regression
   suite. New delivery APIs use the same request gates. Displayed model and owner
   text uses text nodes; new result rendering does not introduce HTML injection.
3. **Verified with limits: dependencies and publication contents.** `pip-audit`
   2.10.1 found no known advisories in the 63 locked runtime packages, including
   the new XML dependency. Signature scanning found no matching credential
   material across 1,082 historical Git blobs at the audit baseline. The shipped
   scan also rejects private runtime paths and tracked symlinks. These checks do
   not recognize every possible secret or unknown vulnerability.
4. **Reviewed static-analysis alerts.** Bandit on Python 3.12 parsed all scoped
   modules. After the XML fix it reported 5 high, 27 medium and 167 low heuristic
   alerts. The five high alerts are four MD5 uses for document cache/readout names
   (not authentication or evidence hashes) and the intentional approved shell
   execution backend. Other reviewed patterns include trusted local code bundles,
   explicit URL endpoints, allowlisted SQL table names and runtime temporary paths.
   These counts are not five confirmed exploitable vulnerabilities and have not
   been hidden with blanket suppressions.

## Boundaries that remain

> **Update for 0.4.0-alpha.10 (2026-09-25):** the first two boundaries below describe alpha.9 and
> are superseded. Every API now requires the owner access key or an owner session, and LAN
> listeners require TLS. Workers, verification commands and managed services run only inside
> Linux bubblewrap, with no unsandboxed fallback; native macOS and OAuth worker execution are
> disabled. Network access and the host kernel remain shared. See [SECURITY.md](../SECURITY.md).

- **Trusted single operator / trusted LAN only.** Studio has no multi-user login,
  RBAC or tenant isolation. The request token is a browser-request defense, not
  identity authentication. A client on the allowed network can obtain a session
  token. Do not expose the port to an untrusted network or the public internet.
- **Native execution is not an OS security sandbox.** Approved model commands
  have the service account's permissions. Separate review and a smaller prompt do
  not prevent a malicious command from acting with those permissions. Use a
  dedicated account and independently configured sandbox for untrusted workloads.
- Automatic tool approval remains an explicit owner/company setting. Process
  modes do not enable it. Local acceptance is not evidence of deployment or live
  CRM, communications or other external integration health.
- Long-running operation across restarts is regression-tested; a continuous
  seven-day autonomous company operation has not been demonstrated by this audit.
- Packages are source distributions for macOS/Linux/Windows via WSL2, not native
  signed installers. Test receipts and release manifests describe what was built.

## Reproduce validation

```sh
./setup-studio
frontier/.venv/bin/python scripts/ci_check.py
uv export --project frontier --locked --no-default-groups --extra document-readers \
  --no-emit-project --no-hashes --format requirements-txt --output-file /tmp/miner-runtime.txt
uv tool run --python 3.12 --from pip-audit==2.10.1 pip-audit \
  -r /tmp/miner-runtime.txt --disable-pip --no-deps
```

The local verification receipt records executed tests, commit, dirty-worktree
status and verified archive hashes. Publication requires a passed receipt for the
clean published commit and a successful locked dependency audit. A dirty receipt
is not proof of a published commit. Checks run locally or on the operator's own
server; GitHub Actions is intentionally not used or required. No `workflow`
authorization is needed, and auto-merge is not enabled.

Policy update: the owner explicitly declined GitHub Actions after the initial
audit. The previously prepared hosted workflow was never published or executed.
Local macOS/Linux verification remains the delivery gate; hosted CI is no longer
an outstanding requirement. This supersedes the CI authorization note in the
original alpha.9 source archives without changing their tested runtime code.
